# R3/R4: the H37 and Heath CP/M disk formats

Phase 0 research for HCOS v2 (PLAN.md section 8, items R3 and R4).

**Sources.** Heath CP/M 2.2.03 `BIOS.SYS` from the H17/H37 boot disk
(`H89/disks/CPM-2-2-03-64K-H17-H37-BOOT_00A3A2A6.H37`, identical to the one
in `HCOS/build/disks/cpm37.h37`) and from the H17 disk
(`HCOS/build/disks/cpm.h8d`). Both were relocated with their bitmaps and
disassembled. Also used: `FORMAT.COM` 2.03 from the H37 disk, the boot
records of both disks, the emulator's `core/devices/H37.*`,
`core/media/SoftDisk.*` and `Machine.cpp`, an `h89run --trace-io` boot of the
H37 disk, and `testHdos/source/acm/h37def.acm` and `labdef.acm` from
mgarlanger/asmx.

**asmx doesn't have the HDOS DK driver source.** It has only
`H37DEF.ACM`, the port and bit definitions, and they agree with the BIOS.
Everything below about Heath's H37 code comes from the CP/M BIOS.

Addresses are those of the E800H build (H17/H37) unless they say otherwise.

## 1. The controller (Z-89-37: WD1797 + two latches)

| Port | Dir | Use |
|---|---|---|
| 170Q 78H `DK.CON` | W | control latch (write-only, so the BIOS keeps a copy at 0025H) |
| 171Q 79H `DK.INT` | W | interface latch: bit 0 = 1 makes 7AH/7BH the sector/track registers, 0 makes them command-status/data |
| 172Q 7AH | R/W | status / command (bit 0 of 79H = 0); sector (bit 0 = 1) |
| 173Q 7BH | R/W | data (bit 0 of 79H = 0); track (bit 0 = 1) |

Control latch, 78H (`CON.*`):

| Bit | Meaning |
|---|---|
| 0 | INTRQ interrupt enable (RST 4, level 4, 0020H) |
| 1 | DRQ "interrupt" enable (ends a HALT, see below) |
| 2 | MFM (double density) |
| 3 | all motors on |
| 4-7 | drive select DS0-DS3 (one-hot) |

**Side** isn't in the latch. It is the 1797's SSO pin, set by the U bit
(02H) of each Type II/III command. **The 1797 is clocked at 1 MHz** (5.25"),
so the step-rate codes r1r0 = 0-3 mean 6, 12, 20 and 30 ms, and the E delay
is 30 ms.

The 1797 commands Heath uses:

| Command | Byte | Notes |
|---|---|---|
| Restore | 00H + rate | no head load, no verify |
| Seek | 18H + rate | head load, no verify. Track register = current, data register = target |
| Read Sector | 88H (+02H for side 1) | b = 1 (IBM length codes 128-1024), single sector, no E delay |
| Write Sector | A8H (+02H) | |
| Read Address | C0H / C2H | used only at login |
| Force Interrupt | D0H | reset/idle |

**Data transfer: HALT plus DRQ, ended by INTRQ.** No byte is counted and
no status bit is polled. The read loop (F16CH):

```
        lda  0025h ! ori 02h ! out 78h     ; DRQ enable on
        xra a ! out 79h                    ; command/data registers
        mov a,b ! lxi h,LOOP ! out 7Ah     ; issue Read Sector
LOOP:   hlt                                ; DRQ ends the HALT
        in 7Bh ! stax d ! inx d ! pchl     ; Z80: about 35 T a byte
```

The write loop is `ldax d / hlt / out 7Bh / inx d / pchl` (the byte is
fetched before the HALT).

- **DRQ.** With control bit 1 set, DRQ asks for an interrupt and the card
  answers the acknowledge with an `EI` opcode, so the CPU just goes on after
  the HALT. Interrupts must be enabled. **While bit 1 is set, the card
  blocks the other interrupt levels**, so 2 ms clock ticks are held off
  during a sector. This is the emulator's model (`Machine::intAck`). On the
  real card it is [UNVERIFIED].
- **End of command.** INTRQ comes in at RST 4, and the BIOS puts
  `JMP F248H` at 0020H at cold boot. The handler waits a little, reads
  status (which clears INTRQ), replaces its own return address with the
  word at 0026H (the "completion address" the caller stored), then does
  `EI` and `RET`. So the transfer loop is left by a jump to the completion
  routine, with the status in A. Type I commands use the same trick: they
  store the completion address, issue the command and spin in `JMP $`
  (F15DH).
- **Timing.** A Z80 at 2.048 MHz has about 65 T per MFM byte (32 µs) and
  131 T per FM byte (64 µs). Polling DRQ on 7AH costs about 27 T a test, and
  about 60 T a byte with the store. That is fine for FM but marginal or
  impossible for MFM. So **the HALT method is needed for double density.**
  For writes, DRQ is raised when the ID is found and the first byte must
  arrive before the data mark, so the routine has to be in the loop already.
  The BIOS waits about 70 µs (`mvi a,0Ah` loop) after a command before it
  reads status.
- **No disk / no index.** Without index pulses the 1797 never gives up a
  Type II command. Heath checks for rotation at login (below).

Timers (the 2 ms clock ISR at F405H, counter at 000BH):

| Counter | Unit | Use |
|---|---|---|
| F404H | 4 ms | settle and motor-start wait. Every seek sets it to at least 5 (20 ms). Starting a stopped motor: 251 (about 1 s), or about 62 (about 250 ms) if bit 7 of DPH ext byte 5 is set. A new drive with the motor running: 14 (56 ms). Same drive: 0 |
| 0023H | 512 ms | motor off (latch bit 3) after 15 (about 7.7 s) |
| 0024H | 512 ms | drive selects off (latch &= 0FH) after 6 (about 3 s) |

## 2. How Heath's H17/H37 BIOS drives it

**Structure.** The BIOS has a table of 6 DPHs (E84EH, 24 bytes each), with
3 H17 drives and then 3 H37 drives. Each is a standard 16-byte DPH followed
by an **8-byte extension**:

| Ext byte | Meaning |
|---|---|
| 0 | flags. Bits 7-5: controller (010 = H17, 011 = H37). Bit 4: double-step (48-tpi disk in a 96-tpi drive, set at login). Bit 3: 96-tpi drive (FORMAT uses it to choose 40 or 80 tracks). Bit 2: 1024-byte sectors. Bit 1: MFM. Bit 0: two-sided |
| 1 | drive-select bit for the latch (H17 02/04/08H; H37 10/20/40H) |
| 2 | 128-byte records per physical sector (2/4/8) |
| 3 | records per block (unallocated-write count for deblocking) |
| 4 | current cylinder; 80H = unknown, so restore first |
| 5 | bit 7: fast motor start. H37: bits 1-0 are the 1797 step rate. H17: bits 6-0 are the step time in 2 ms ticks |
| 6 | bit 1: logical drive sharing a physical drive (the "PUT DISK . IN DRIVE ." prompt); the other bits come from the label |
| 7 | the logical drive now mounted on a shared drive |

The defaults on this disk are: H17 drives `40 xx 02 08 FF 0A 00 00`; DK0
`62 10 02 08 80 02 00 00`; DK1 `6A 20 02 08 80 82 00 00`; DK2
`62 40 02 08 80 03 02 00`. They are patchable by CONFIGUR [UNVERIFIED].

SELDSK maps the logical drive through a byte map at 0040H-004FH to a DPH.
At cold boot it builds the map so that the boot controller's drives come
first. The disk code then dispatches through a 5-entry vector per
controller type, chosen by ext0 bits 7-5. The vectors are login, read, write,
reset and home. The H17 vector is at ED50H and the H37 vector at F058H; other
types get an error vector.

**Deblocking (EA83H-EC70H)** is DRI's blocking/deblocking algorithm from
the CP/M 2.2 Alteration Guide, made general: records per host sector come
from ext2 and the unallocated count from ext3. There is one host buffer of
**1024 bytes** at F84FH (it overlays the cold-boot code), with
hstact/hstwrt/unacnt at F84CH-F84EH. The host sector is the record index
divided by records per sector, and host sectors are numbered from 1.
**There is no XLT for H37 drives.** The interleave is in the sector IDs
FORMAT writes [interleave UNVERIFIED].

**Two-sided disks** (F257H): each logical track is one side. Cylinder =
track/2 and side = track AND 1, so the reserved tracks of a two-sided disk
are cylinder 0 side 0, cylinder 0 side 1, and so on.

H37 driver outline (F058H-F404H):

| Routine | Address | What it does |
|---|---|---|
| select | F2A6H | latch = ext1 + (MFM if ext0 bit 1) + motor + INTRQ enable. Sets the motor or settle wait (table above). Clears the timers 0023/0024H |
| setup | F257H | retries = 4 (2 during login). Works out cylinder and side from the track. If ext4 = 80H it restores, otherwise it loads the track register from ext4 |
| restore | F2EEH | delay, then ext4 = 0 and Restore + rate, waiting for INTRQ |
| seek | F32AH | if the target isn't the current cylinder: Seek. With double-step it puts the old cylinder back in the track register and seeks again, which gives 2 steps a cylinder. Then the track register and ext4 = target, settle 20 ms or more, sector register = sector, and wait for the timer |
| read | F1ACH | setup, seek, Read Sector 88H + side into the host buffer through the HALT loop, then retry |
| write | F1CEH | the same with A8H. Write is refused if ext0 bit 4 is set (no writing to 48-tpi media in a 96-tpi drive) |
| errors | F217H | status AND C0H (not ready or write protect): fail at once. Otherwise the soft-error count at E84BH goes up and there is another try; with 2 tries left it restores first. When the tries run out it prints `H37 READ/WRITE ERROR xx` and returns failure |
| ready | F391H | waits out the motor delay, sends Force Interrupt, then counts index edges (status bit 1) for 200 ticks (400 ms). 2-6 edges = turning, otherwise "not ready" (80H) |
| done | F193H | latch DRQ enable off, timers 0023H = 15 and 0024H = 6 |

**Login (F067H): the density and the format come from the disk.**

1. The ready check, then ext4 = 80H (forces a restore).
2. Read track 0 sector 1 in the density in ext0 bit 1. If that fails,
   **flip ext0 bit 1 and try again.** This is the density probe.
3. **Label check:** the sum of bytes 04H-1CH of that sector, plus 1, must be
   0. If the label is bad and the disk is MFM, it is an error. If it is bad
   and the disk is FM, the BIOS uses a built-in default label (F13EH), which
   is the H17 layout.
4. From the label it copies: ext0 bits 2-0 from byte 05H, ext2 from 07H,
   ext3 from 08H, ext6 from 0BH (keeping bit 1), and the 15-byte DPB from
   0DH into the drive's RAM DPB.
5. Two-sided (label bit 0): Read Address on side 1 must return head byte 1.
6. TPI: seek to cylinder 2 and Read Address. An ID of track 2 is fine. An ID
   of track 1 means a 48-tpi disk in a 96-tpi drive, so it sets
   double-step (ext0 bit 4). Anything else is an error.
7. Restore, then set the timers.

**The H17 driver (ED50H-F057H, 776 bytes)** is the same code as in the
H17-only BIOS. It reads no label: its login only checks rotation through
the H17's index bit. Its DPB is fixed (section 3).

**Size:** `BIOS.SYS` code is 12FEH = 4862 bytes, assembled at 0000H and
loaded at E800H. With buffers, allocation vectors and stack it runs from
E800H to about FF2CH, **5.8K resident**. The H17-only BIOS is 0EB4H = 3764
bytes at F000H and runs to about FF12H (3.8K).

## 3. R4: the DPBs and how a disk is recognised

**H17 (both BIOSes, fixed, the only H17 format):** SS, 40 tracks,
10 x 256 bytes, hard-sectored FM.

| SPT | BSH | BLM | EXM | DSM | DRM | AL0 AL1 | CKS | OFF |
|---|---|---|---|---|---|---|---|---|
| 20 | 3 | 7 | 0 | 91 | 63 | C0 00 | 16 | 3 |

XLT (records, from 1): `1 2 9 10 17 18 5 6 13 14 3 4 11 12 19 20 7 8 15 16`.
That is 256-byte sectors 0,4,8,2,6,1,5,9,3,7, a skew of 4 by sector pairs
(the emulator's `kH17Skew` agrees). The H17 BIOS keeps it at FC1BH/FC2AH; the
H17/H37 BIOS keeps it at F829H/F838H.

**H37 (taken from the disk's label).** Both BIOSes accept any DPB a valid
label has. The formats Heath makes are FORMAT 2.03's table at 0B7AH. Each
entry is 19 bytes: label flags, records per sector, records per block, TPI
(0 = 48, 1 = 96), then the DPB. **No H37 format has an XLT.**

| # | Format | Phys sectors | SPT | Block | EXM | DSM | DRM | AL0 | CKS | OFF | Capacity |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 0 | SS SD 48 | 10 x 256 FM | 20 | 1K | 0 | 91 | 63 | C0 | 16 | 3 | 92K |
| 1 | DS SD 48 | 10 x 256 FM | 20 | 1K | 0 | 191 | 127 | F0 | 32 | 3 | 192K |
| 2 | SS DD 48 | 16 x 256 MFM | 32 | 1K | 0 | 151 | 127 | F0 | 32 | 2 | 152K |
| 3 | DS DD 48 | 16 x 256 MFM | 32 | 2K | 0 | 155 | 255 | F0 | 64 | 2 | 312K |
| 4 | SS "ext" 48 | 5 x 1024 MFM | 40 | 1K | 0 | 189 | 127 | F0 | 32 | 2 | 190K |
| 5 | DS ext 48 | 5 x 1024 MFM | 40 | 2K | 0 | 194 | 255 | F0 | 64 | 2 | 390K |
| 6 | SS SD 96 | 10 x 256 FM | 20 | 1K | 0 | 191 | 63 | C0 | 16 | 3 | 192K |
| 7 | DS SD 96 | 10 x 256 FM | 20 | 2K | 1 | 195 | 127 | C0 | 32 | 3 | 392K |
| 8 | SS DD 96 | 16 x 256 MFM | 32 | 2K | 1 | 155 | 127 | C0 | 32 | 2 | 312K |
| 9 | DS DD 96 | 16 x 256 MFM | 32 | 2K | 0 | 315 | 255 | F0 | 64 | 2 | 632K |
| 10 | SS ext 96 | 5 x 1024 MFM | 40 | 2K | 1 | 194 | 127 | C0 | 32 | 2 | 390K |
| 11 | DS ext 96 | 5 x 1024 MFM | 40 | 2K | 0 | 394 | 255 | F0 | 64 | 2 | 790K |

AL1 is 00H throughout. The label flags are bit 0 DS, bit 1 DD and
bit 2 1024-byte sectors, so the flag values are 0, 1, 2, 3, 6 and 7. SPT is
per side. 512-byte
sectors are allowed by the BIOS (ext2 = 4) but FORMAT doesn't make them.
**One density for the whole disk:** the BIOS applies ext0 bit 1 to every
track, track 0 included. The emulator's `kH37DoubleLayout` is format 8.

**The label** is the first sector of track 0 (the boot record), bytes
04H-1CH:

| Offset | Contents (CP/M H37 disk / H17 disk) |
|---|---|
| 00-02 | `JMP 229DH` (boot code) |
| 03 | 60H / 40H, the controller type; not checksummed, use [UNVERIFIED] |
| 04 | 00 |
| 05-0C | an image of the 8-byte DPH extension at format time: `60 10 02 08 00 02 00 33` / `40 02 02 08 03 0F 00 00`. The BIOS takes only 05 (bits 2-0), 07, 08 and 0B. What 0C (33H) means is [UNVERIFIED] |
| 0D-1B | DPB (15 bytes) |
| 1C | check byte: sum(04H-1CH) + 1 = 0 |

**How a disk is recognised:**

| BIOS | Method |
|---|---|
| H17 | none. The format is fixed, and the H17 label (which these disks have, valid) is ignored |
| H37 | try T0S1 in each density. A valid label gives sides, sector size and DPB. No label on FM gives the default SS SD 48 (= H17 DPB). No label on MFM is an error. Then a Read Address check for sides and TPI |

**An HDOS disk** has no CP/M label (the bytes don't check), so Heath's BIOS
mounts it as SS SD with the CP/M DPB and its directory is garbage. HCOS has
to look for the HDOS label at track 0 sector 9 (`LAB.*` in `labdef.acm`:
SIZ, PSS, VFL bit 0 = 2 sides, bit 1 = 96 tpi, SPT).

**The images in `H89/disks`:**

| Image | Geometry (trailer) | Format |
|---|---|---|
| `CPM-2-2-03-64K-H17-H37-BOOT_*.H37` | `SPT=10 SSZ=0256 TRK=40 SID=1 FM` | Heath CP/M H37 SS SD 48 (#0), valid label (`60 00 60 10 02 08 00 02 00 33` + H17 DPB) |
| `HDOS-2-H37IMGR-AND-H8DIMGR3_*.H37` | the same | HDOS: label at 900H, SIZ 400, PSS 256, VFL 0, SPT 10. No CP/M label |
| `CPM_2-2-03.H8D` | 100K H17 | H17 format, label valid (`40 00 40 02 02 08 03 0F 00 00` + DPB) |
| `HDOS_2-0_System.h8d` | 100K H17 | HDOS |

**Both H37 images are SS SD 40-track FM, 10 x 256: the same geometry as the
H17.** No double-density image is available, although CP/M FORMAT in the
emulator can make one.

## 4. The H37 system tracks (CP/M boot disk)

A byte stream from track 0 sector 1. On SS SD, 3 tracks = 7680 bytes
(1E00H). DD formats reserve 2 tracks: 8K for 16 x 256 and 10K for 5 x 1024.
DS SD keeps OFF = 3, which is cylinder 0 on both sides and then cylinder 1
side 0.

| Disk offset | H37 disk (E800H build) | H17 disk (F000H build), for comparison |
|---|---|---|
| 0000H | boot record, a full **256-byte** sector with the label (runs at 2280H) | boot record, **128 bytes** (runs at 2280H) |
| CCP | **0100H-08FFH** goes to D200H (copyright at 0118H) | **0080H-087FH** goes to DA00H (copyright at 0098H) |
| BDOS | 0900H-16FFH goes to DA00H (entry DA06H) | 0880H-167FH goes to E200H |
| loader BIOS | 1700H-1A80H goes to E800H (about 900 bytes) | 1680H-1A76H goes to F000H (about 1000 bytes) |
| free | 1A81H-1DFFH (about 895 bytes) | 1A77H-1DFFH (about 905 bytes) |

**Boot.** MTR-90 reads track 0 (the trace shows 2560 data bytes at ROM
0A59H) and enters the boot record at 2280H [R1]. The H37 boot record drives
the 1797 itself. It reads label byte 05H (DD, 1024-byte, DS) and byte 07H,
takes the drive from 2131H, and uses the ROM's INTRQ completion word at
2037H [R1]. It reads 59 records' worth of sectors (30 sectors, 7680 bytes)
to D100H-EEFFH, then switches the motor latch to 08H and jumps to E800H. The
loader BIOS then reads `BIOS.SYS` through the BDOS (v1's KERNEL.md).

**Warm boot** reads 44 records whose load address falls in D200H-E7FFH,
skipping the boot sector. The stream starts at D100H for H37 disks and at
D180H for H17 disks. It goes through the normal deblocking path, using the
boot drive's SPT, so it works for any label format. **This is why v1 found
the CCP at 100H on H37 disks and 80H on H17 disks.**

**For HCOS:** a 2K shell, 3.5K BDOS and the boot record need 5.75K. That
fits in the 7.5K of SS SD (about 1.7K spare). The H37 boot record must be a
whole sector, so the stream starts at 100H.

RAM after the code: host buffer 1024 (F84FH), DIRBUF 128, H17 ALV/CSV
3 x 28 = 84, H37 RAM DPB + ALV(50) + CSV(64) 3 x 129 = 387, variables 46,
type-ahead 40, stack about 48. **About 1.75K.**

The H17-only BIOS (F000H) has the same parts without the H37:
3137 bytes of code and tables. The disk-entry, deblocking and error part,
the H17 driver and the character I/O are byte-for-byte the same size
(897, 776 and 763). The clock ISR is 102 bytes. RAM is a 256-byte buffer,
DIRBUF, 3 x 28 and the rest.

**The H37 costs Heath about 2.1K:** 941 for the driver, 42 for the ISR
timers, 72 for the DPHs, 768 more host buffer and 387 for the RAM
DPBs/ALVs/CSVs. That is the 5.8K - 3.8K difference.

H37 driver functions (from the table above, in bytes): select/motor 72,
setup 79, seek with double-step 103, restore and reset 69, ready (index
count) 76, read 34, write 73, transfer loop and ISR 54, errors 49, login
with label, density, sides and TPI 215, default label and ID buffer 31,
the rest about 86.

## Implications for HCOS v2

**Formats for 2.0.** Support:
- H17 SS SD (the fixed DPB and skew above);
- H37 SS SD 48 tpi, 10 x 256 FM (format #0: both available H37 images; CP/M
  with a label, or HDOS);
- H37 DS SD and 16 x 256 MFM (formats 1-3, 6-9) as an option, since
  they cost only side, density and DPB-copy code.

Don't support in 2.0: 1024-byte sectors (formats 4, 5, 10, 11). They alone
force a 1024-byte host buffer. Also leave out double-step and Heath's
shared-drive prompt.

**Recognition.** Read T0S1 (FM first, then MFM). If the CP/M label checks,
take the DPB from it into a RAM DPB per drive, and reject flags or sector
sizes HCOS doesn't support. Otherwise, if sector 9 has an HDOS label, mark
the drive HDOS. Otherwise use the default SS SD DPB. This matches Heath, so
HCOS-formatted disks stay Heath disks.

**Driver design.**
- The same HALT/DRQ loop and INTRQ completion jump at 0020H. It must run
  with interrupts on, and it holds off the clock, so count ticks with the
  clock flip-flop in mind.
- Keep a copy of the latch in RAM. Keep the motor and deselect timers in
  the existing 2 ms clock ISR, at about 25 bytes.
- 4 retries with a restore halfway, and no retry on not-ready or write
  protect.
- A rotation check (index edges) or a clock watchdog with Force Interrupt,
  because a 1797 with no disk never finishes.
- Seek with a 20 ms settle and the step rate from a per-drive byte.
- One deblocking layer shared with the H17, with records per host sector
  from a per-drive byte. Heath's general DRI algorithm already does this.

**Byte estimate.**

| Item | SD SS only | + DS, MFM 256 |
|---|---|---|
| H37 driver code | about 300 | about 450 |
| H37 DPH/ext, 3 drives | 60 | 60 |
| H37 RAM: ALV+CSV (+ RAM DPB) per drive x 3 | 84 | 3 x (15+40+64) = 357 |
| host buffer | 256 (shared with H17) | 256 |

A whole HCOS v2 BIOS, estimated: jump table 51, warm boot about 150,
console + clock + memory switch about 250 [R5], disk entries + deblocking
about 450, errors about 80, H17 driver about 776 [R2/R6], H17 tables about
110, DIRBUF 128, H17 ALV/CSV 84, variables and stack about 130. That comes
to **about 2.2K before the H37.** With the SD-only H37 it is **about 2.9K**;
with DS/MFM-256 it is **about 3.4K.** Both fit in 4K at F000H, with the
cold-boot code overlaid in the host buffer as Heath does it. Heath's full
set with 1024-byte sectors (+768 buffer, larger driver) would come to about
4.2K and not fit. So **H17 + H37 in one 4K BIOS is feasible** if 2.0 leaves
out 1024-byte sectors, double-step and Heath's IOBYTE, printer and
type-ahead character I/O (763 bytes in Heath's).
